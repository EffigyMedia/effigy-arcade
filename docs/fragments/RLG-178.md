### RLG-178 — Every run opens with a PURSUIT x1 banner nobody asked for

TRACKED, NOT STARTED. Owner, 2026-09-08: "Every run starts with a banner that says pursuit x1.
What is that and why do we need it?"

TWO QUESTIONS AND THE SECOND IS ALREADY ANSWERED. Whatever it is for, a banner that fires on
every single run at the same moment is telling the player something they cannot act on, in the
first seconds, before anything has happened. The owner does not want it.

WHAT IT ALMOST CERTAINLY IS, stated as a lead and not as a finding: the pursuit system uses
`flashWarn` for its messages - `flashWarn('SPEED TRAP')` is one - and the wanted level is drawn
in stars. A banner reading "PURSUIT x1" at the start of a run looks like a heat readout being
announced when the pursuit setting is switched on, rather than when a pursuit begins. If so it
is a message about a SETTING wearing the clothes of a message about an EVENT, which is why it
reads as noise.

THE FIX DEPENDS ON WHICH IT IS, so find the call site before removing anything. A banner that
announces the pursuit setting should not exist. A banner that announces a real pursuit starting
may be worth keeping and merely fires too early.
- **RULED 2026-09-08T20:43:06-04:00** — ### 2026-09-08 — built, and the lead in this record was right

**THE ROW IS KEPT AND THE TEST INSIDE IT IS FIXED.** The guess written above was that a message
about a SETTING was wearing the clothes of a message about an EVENT. It was close but not what
it turned out to be. `#pursuit` is a permanent HUD row, not a banner, and it is a live count of
the cruisers on you — a good thing to have while one is happening. **What was wrong is when it
fired.**

**IT COUNTED `onPlayer !== false`.** A police car that has never chosen a target has `onPlayer`
set to **undefined**, and `undefined !== false` is true. The road lays a speed trap within the
first seconds of every run, so the row counted a car parked on the verge that had not looked at
anybody — which is exactly the "×1" the owner saw, every run, blinking red.

**THE SAME MISTAKE, IN THE SAME SHAPE, WAS FOUND THE SAME DAY IN THE BOX** ([[RLG-173]]): the
box test asked whether a car was *not* the player, and a parked trap passed it and took a
station. `!== false` gets written when `=== true` is meant, and it is invisible until something
in the game legitimately holds "undecided" as a third state. Now that a cruiser commits once and
records its choice, that third state is common. **Anywhere else in the police code that asks
`!== false` should be read with this in mind** — `road.js:15729` and `15911`, the cooling clock
and the chase test, both still do, and both were left alone because a cooling clock that treats
an undecided car as a chaser is failing safe.

**THE COMBO SUFFIX WAS DELETED WITH IT.** The row appended ` · ×N` when `combo > 1`. `combo` is
set to zero at every reset and nothing anywhere raises it — the score system it belonged to was
removed, and the near-miss handler at `road.js:16356` already carries a note about this same
variable printing "+0" over the road. The guard could never be true.

**PROVED BY `tools/pursuit-row-test.py`**, which reads the row **off the page** rather than
recomputing the predicate. That matters: the complaint is about something the owner SAW, and a
check that asked `cops` the same question the broken line asked would have agreed with the bug.
Restoring the old predicate in place, the check fails and reproduces the report exactly — **lit,
reading ×1, opacity 1, on 90 of 90 samples of a legal drive past parked traps**.

**AND THE HARNESS READS OPACITY ONLY AFTER A SETTLE.** The row fades over 0.2 seconds, so a
sample taken the instant the class lands reads `opacity: 0` on a row that is working perfectly.
A first version reported exactly that and would have made a working row look broken — or, worse,
made "it is hidden" look proven when the reading was merely early.
