### RLG-089 — Race mode always has checkpoints, whatever the timed toggle says
- **RULED 2026-08-30T20:24:34-04:00** — Owner, 2026-08-30: the checkpoints do not spawn in RACE mode if TIMED was turned off while TEST DRIVE was selected. Turning TIMED back on, switching to RACE and then driving still starts a run with no checkpoints in it. Race mode is expected to be timed inherently, so its checkpoints must always be spawned.

THE SHAPE OF THIS IS A SETTING OUTLIVING THE MODE IT BELONGED TO. TIMED is a choice about a test drive, where running without a clock is a reasonable thing to want. In a race it is not a choice at all - a race is against a clock by definition - so the toggle should not be able to reach into it. The defect is that one screen's option is being read by a mode that has no business consulting it.

SO THE FIX IS NOT TO RE-SPAWN THE CHECKPOINTS. It is to stop RACE from asking. Whatever decides a checkpoint exists must read the MODE first and the toggle only where the toggle applies; a patch that spawns them again on entering race would leave the same wrong question being asked somewhere else.

AND THE ORDER THE OWNER FOUND IT IN MATTERS. Timed off under test drive, timed on, then race, then drive - it still failed. That says the state is being decided once and kept, rather than being read at the start of the run, so the check has to reproduce that sequence rather than simply starting a race with the toggle off.
- **RULED 2026-08-30T20:43:02-04:00** — BUILT, 2026-08-30. There is no condition on placing a checkpoint board any more.

THE WRONG QUESTION WAS BEING ASKED TWICE OVER. The loop that places the boards already sits inside clockRuns(), which is mode === 'race' || timedRun and is exactly the right test - it was written for this. The next line then asked timedRun on its own and got a different answer, so in a race with the toggle off the clock ran and the boards did not appear.

AND IT CONSUMED THEM RATHER THAN DEFERRING THEM. nextCP++ ran whether or not a board was pushed, so each checkpoint was counted past and thrown away. Turning the toggle back on mid-run could not have recovered the ones already skipped, which is the part of the report that looked like the setting was being ignored.

THE OWNER'S OWN SEQUENCE DOES NOT REPRODUCE IT, AND THAT IS WORTH RECORDING. Timed off under test drive, timed back on, then race: the harness walks exactly that and it PASSES on the broken build, because the toggle ends up on and the old line then places the board. What breaks it is TIMED left OFF while a race runs. Both cases are in race-test - the reported sequence because it is the report, and the discriminating one because it is the only one that fails on the old code: 0 boards with the clock reading 41.9, against 1 board on the fix.

AND THE CHECK COUNTS BOARDS, NOT SETTINGS. A check written against clockRuns() would have passed on the broken build, because clockRuns() was already right - it was the line beside it that was wrong.

THE HARNESS HAD TO DRIVE FURTHER THAN IT LOOKS. A checkpoint sits every two miles, about 167,000 world units, and the placing loop only looks 90,000 ahead. Four seconds at nine tenths of top speed covers 55,000, so the first version drove a third of the way to the first board and reported that none had been placed - which is the defect it was looking for, found in its own arithmetic.
