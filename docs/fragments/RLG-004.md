### RLG-004 — pack.sh checks cache agreement before it regenerates assets.js, so a version bump deadlocks the build
- **RULED 2026-08-28T09:40:55-04:00** — - **The defect.** `pack.sh` section 3 validates that `sw.js` and `assets.js` name the same cache
  generation. Section 4 regenerates `assets.js` from `sw.js`. **The check runs first.** So bumping
  the cache version in `sw.js` - which is required whenever a `CORE_FILES` asset changes - makes the
  build refuse, and the only way past is to hand-edit the generated file that section 4 is about to
  overwrite anyway.

- **How it surfaced.** A new icon shipped, `icon.png` is in `CORE_FILES`, so the generation was
  bumped v24 to v25 and the build refused: `assets.js says effigy-arcade-core-v24, sw.js says
  effigy-arcade-core-v25`. `assets.js` was seeded by hand to get through, once.

- **Why the gate itself is right and must stay.** It guards a failure that shipped once: the cache
  name was hardcoded in two places, the game folders were renamed, neither was bumped, and the
  worker kept serving a cached `index.html` that pointed at folders the server no longer had -
  eighteen files, all 404, behind a green build.

- **The fix.** Regenerate, then verify. In `--check` mode there is nothing to regenerate, so the
  comparison stands as it is; in build mode the agreement check belongs after section 4, comparing
  what was just written. **Do not weaken the check to a warning** - the drift it catches is exactly
  the drift that shipped.
- **RULED 2026-08-30T11:04:50-04:00** — REGENERATE, THEN VERIFY. Built exactly as the fragment ruled, and the fragment's insistence that the
check must not be weakened is the reason it is worth recording rather than just doing: the order was
the bug, and the temptation with a gate that fires wrongly is always to soften it.

`assets.js` is GENERATED and takes its version from `sw.js`, so in a build the two agree by
construction the moment the generator has run. The comparison ran before it, so a bump to `sw.js`
failed the build that would have fixed it - and the way past that, once, was to seed `assets.js` by
hand, which is exactly the drift the check exists to catch being introduced by the check itself.

ONE DEFINITION, TWO CALLERS. `cache_agrees` is a function now rather than three lines inline.
`--check` has nothing to regenerate so it asks before, on the files as they are; a build asks after,
on what it just wrote. The sw.js-internal check - core and runtime naming the same version - stays at
the top in both, because that one is about `sw.js` alone and no regeneration can fix it.

PROVEN BY REPRODUCING THE FRAGMENT'S OWN SCENARIO. Bump `sw.js` to v27 and leave `assets.js` at v26:
`--check` refuses with "assets.js says effigy-arcade-core-v26, sw.js says effigy-arcade-core-v27",
which is the report that must survive, and the build then succeeds, regenerates, and verifies at v27.
Before this change that build refused.

AND THE VERSION WAS PUT BACK. Nothing shipping changed, so the cache stayed at v26: bumping it would
have thrown away every device's cache to prove a point about the packer.
