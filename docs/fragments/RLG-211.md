### RLG-211 — A driving cabinet takes minutes to boot when Chrome's GPU path is unhealthy
- **RULED 2026-09-11T09:47:28-04:00** — **MEASURED 2026-09-11, AND IT CORRECTS A CONCLUSION THIS PROJECT ALREADY WROTE DOWN TWICE.**

**THE NUMBERS.** Same machine, same minute, same build, service workers blocked, installed Chrome
headless:

    interstate, GPU as Chrome left it     BOOTED in 338.9s     domInteractive 338,835ms
    interstate, --disable-gpu             BOOTED in   2.8s     domInteractive   2,752ms
    quietus,    GPU as Chrome left it     BOOTED in   0.6s
    launcher,   GPU as Chrome left it     BOOTED in   0.5s
    road.js fetched in 15-18ms in every one of them

Three separate runs of the driving cabinet took 207s, 259s and 339s. The software-rendering path
took 2.8s. That is a factor of about 120, on one page, on a machine sitting at 8 per cent CPU across
sixteen cores with 41GB of memory free.

**SO IT IS NOT THE NETWORK, NOT THE FILE SIZE AND NOT THE MACHINE BEING BUSY.** `road.js` is 1.5MB
and arrives in under twenty milliseconds. The launcher and Quietus - same browser, same server, same
moment - open in half a second. The only page affected is the one that does heavy CANVAS work at
boot: the driving engine builds its sprite sheets up front, more than a hundred canvases across the
rival bodies and paints, and every one of those is a draw and a readback.

**THE LEADING EXPLANATION, STATED AS ONE.** Chrome's accelerated canvas path degrades into a state
where each of those operations stalls, and `--disable-gpu` takes it out of the equation by using
software rendering for everything. The mechanism is inferred from the timings rather than observed -
`chrome://gpu` is not reachable under automation, so nothing here has read Chrome's own account of
its GPU state, and that is the next thing to get.

**AND IT RE-READS [[RLG-208]].** That ruling recorded this machine failing to fire `load` for the two
driving cabinets on 2026-09-09 and 2026-09-10, found `window.__road` present with
`document.readyState` stuck at `interactive`, and called it environmental - a document that never
completes. **The document was completing. It was taking minutes.** The engine was up and answering
because `road.js` had finished; what had not finished was whatever the page does after
DOMContentLoaded, on the same stalled path. Both observations are the same defect seen at different
moments, and "the document never completes" was a description of the symptom rather than a cause.

**RLG-208'S FIX IS STILL RIGHT, AND FOR A BETTER REASON THAN IT GAVE.** Waiting for the ENGINE rather
than for the document is what let the suite run at all through this - and it is why the suite kept
passing this morning while the page was taking a minute to open. That is also the uncomfortable part:
a harness that waits for the engine will happily measure a build that takes four minutes to open and
never say so.

**WHAT THIS MIGHT MEAN FOR A PLAYER, WHICH IS THE PART THAT MATTERS.** This is a desktop Chrome
whose GPU path went bad. A phone is not this machine and nothing here measures one. But the shape of
the risk transfers: the driving cabinets do a large amount of canvas work before the first frame, and
on any device where that path is slow the cabinet does not open slowly - it appears not to open at
all. Quietus and the launcher would be unaffected, so the arcade would look like it had two broken
machines. **The owner has never reported this on a device and it may never happen on one.**

**THREE THINGS TO DECIDE, AND NONE OF THEM SHOULD BE TAKEN QUIETLY.**

    1. WHETHER THE HARNESSES PASS `--disable-gpu`. It would make every run fast and comparable,
       and `harness.py`'s own header says the browser that was used is printed ALWAYS, because a
       harness that silently changes what it measures produces numbers that cannot be compared
       between runs. Software rendering is a different engine. `fps-test` and the performance
       survey in particular must NOT be switched silently.

    2. WHETHER THE BOOT-TIME SPRITE BUILD SHOULD BE SPREAD OR DEFERRED. It is a real cost on
       every device, not only a broken one, and it is paid before the first frame.

    3. WHETHER ANYTHING SHOULD WATCH IT. A cabinet that takes four minutes to open passes every
       check in this repository today, because every check waits for the engine and then asks
       its own question. A boot-time ceiling would have caught this in the first run rather than
       the fifth.
