### RLG-090 — A retry starts a new run, not the last one continued
- **RULED 2026-08-30T20:31:17-04:00** — Owner, 2026-08-30: on a time-over, hitting RETRY carries state over into the new run - the example given is starting in a dry biome with snow slipperiness still applied.

THAT IS TWO PIECES OF STATE THAT DISAGREE, WHICH IS WORSE THAN EITHER BEING WRONG. The place is fresh and the grip is not, so the road looks like one thing and drives like another, and nothing on screen explains why the car will not hold a line.

THE SHAPE IS THE SAME ONE RLG-022 JUST HAD. The biome countdown and the flag that says a run has chosen its opening place were both left uncleared at a reset, so a second run inherited the first one's map; they are cleared now. Settled snow, wetness and whatever else the weather leaves behind are the same class of thing and were not part of that unit. Check whether the retry path even reaches reset(), or whether it is a separate route that was written before reset() carried this much.

AND THE FIX SHOULD BE A LIST OF WHAT A RUN OWNS, not another line added to reset(). Two of these have now been found one after the other, which says the failure is that nobody can see at a glance what a run is supposed to start with. Whatever is written down has to be checkable, or the third one arrives the same way.
- **RULED 2026-08-30T20:59:00-04:00** — BUILT, 2026-08-30, AND THE LIST IS THE POINT. Rain, snow, what has settled, the cloud, the storm and the place now live in one freshWorld function that the reset calls, rather than as lines scattered through it. Three of these have been found one after another - the biome countdown, the opening place, and the weather - and every one was module-level world state that no reset cleared. A fourth line would have fixed this one and left the next.

API.worldState REPORTS EXACTLY THE FIELDS freshWorld CLEARS, so the check does not have to be told twice what clean means: add a field to the world, add it to the list, and the check covers it without being edited.

THE HARNESS DIRTIES THE WORLD ON PURPOSE FIRST. A run that happened to be dry would start a clean run and prove nothing, so retry-test puts deep snow, wet road and a storm sky down, asserts they are really there, and only then restarts. With the weather left inherited it fails on every field at once: wet 0.8, snowy 1, settle 0.9, cloud 0.95, storm 1.

AND IT RESTARTS THROUGH THE SAME CALL RETRY AND DRIVE BOTH TAKE, rather than through the menu, so it tests the reset the player gets instead of the button that leads to it.

AND A HALF-UPDATED CACHE IS WHAT THE OWNER WAS ACTUALLY LOOKING AT. Pressing DRIVE gave a black screen with the mirror still drawing, which is the exact symptom sw.js predicts in its own note: the previous game HTML beside the current shared scripts. Eight versions shipped in one evening with the cache names untouched. The rule written there says to bump them whenever a file MOVES or is RENAMED, and nothing had - which turned out to be the wrong question. What matters is whether the files still AGREE, and after a change the size of road.js they do not. pack.sh refused the build until assets.js agreed with sw.js, which is the check that would have caught this on any of the seven builds before it, had it been run at all. It was not run once this session.
- **RULED 2026-08-31T00:18:00-04:00** — AND THE SAME BUG WAS IN THE TWO COUNTERS BESIDE THE BIOME. Owner, 2026-08-31: there is still a pop on GO, maybe the scenery regenerates - why can the state not be started on load and persisted through the countdown and the drive start.

THAT IS EXACTLY THE FIX, AND THE OWNER NAMED IT BEFORE I FOUND IT. A counter left at zero means a roll is DUE. freshWorld zeroed wetNext and cloudNext along with everything else, and the count-in returns from step() before the world runs - so both rolls were deferred to the first frame after GO and happened in front of the player. The biome had this fault and was fixed one version earlier; nothing made me look at the two lines beside it.

THREE INSTANCES OF ONE SHAPE, ALL IN THE SAME FUNCTION. That is the argument for the list this fragment asked for, and it is also the limit of the list: freshWorld collected the STATE correctly and said nothing about which of those fields were counters that mean something is pending. A field set to zero is not always cleared - sometimes it is armed.

THE ROLLS ARE LIFTED OUT OF THEIR STEPPERS so the reset and the frame update call the same code rather than a copy, the run starts AT what it rolled instead of easing toward it from clear and dry, and both counters are armed to a full interval - because a run that has just chosen its weather is not also a run due to change it.

THE CHECK ASKS THE COUNTERS, NOT THE PICTURE. Comparing the world during the count with the world after GO catches this only when the deferred roll happens to produce weather: it came up dry one run in three and passed on a broken build. Asking whether anything is DUE while the car is held is the same question without the lottery, and it fails three runs in three, naming both counters.

AND ONE CHECK HAD TO BE RESTATED RATHER THAN KEPT. retry-test asserted that a fresh run was dry and clear, which was correct while the reset zeroed the weather and left the roll to the drive. It is wrong now: a run rolls its own weather up front and may legitimately start in snow. The expectation was an accident of the old implementation, so it was rewritten to ask what a new run actually means - nothing accumulated survives, what is falling is what this run rolled, nothing is left due, and the last run's values did not come across.
