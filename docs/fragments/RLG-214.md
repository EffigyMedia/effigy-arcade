### RLG-214 — The DEBUG traffic switch lists a car it will not let you drive
- **RULED 2026-09-12T04:20:24-04:00** — **FOUND BY A HARNESS THAT COULD NOT DRIVE A SALOON, NOT REPORTED FROM A DEVICE.** A measurement
needed to put a production car on the road and used the affordance written for exactly that. The
car appeared in the garage, could be selected, and the DRIVE button did nothing at all: no error,
no message, and the run sat on the menu with the clock frozen at 60.0. The harness read that as
zero miles driven and printed it as a finding, which it was not.

## THE MECHANISM, AND IT IS TWO FUNCTIONS THAT DISAGREE

    openBy(k)      widens for the debug switches - it decides what the garage LISTS
    carLocked(k)   never consults them   - it decides whether the car can be DRIVEN

`garageBodies` builds its list through `openBy`, which reads `dbgTraffic`, `dbgRacers` and
`dbgPolice`. The DRIVE button is built and guarded by `carLocked`, which reads the save flags and
nothing else. So a debug-opened car is listed, is selectable, is drawn as a LOCKED silhouette, and
its button reads LOCKED and is `disabled`. Every one of the three debug switches is affected, not
just the traffic one.

## AND THE CODE ALREADY SAYS WHICH SIDE IS WRONG

`carLocked`'s own comment reads: *"ignoring the debug overrides - those open a car WITHOUT writing
the flag, and a car opened for testing should look like a car you own."* The second half states the
intent and the function does the opposite of it - a debug-opened car looks LOCKED rather than owned.
So the comment is the specification and the code does not meet it.

**THE FLAG IS DELIBERATELY NOT WRITTEN AND THAT PART IS RIGHT.** The reason the switches exist is
recorded beside them: *"testing the cars must not consume the moment of winning them."* Whatever
fixes this must keep that - the repair is to let `carLocked` see the override, never to make the
switch write an unlock.

## WHY NOBODY SAW IT

A switch in the DEBUG menu is used by whoever is testing a car, and the garage LIST is what they
look at first. The list is correct. The failure is one screen further on, it is silent, and the
button that refuses says LOCKED - which is exactly what a locked car says, so the screen looks
consistent with itself.

## WHAT IT COST HERE, WHICH IS THE PART WORTH KEEPING

The harness reported `SALOON 0.00 miles` and `STALLION 0.00 miles` beside two real results, and
that reads as a measurement rather than as a refusal. The project's own rule covers this and it was
written for `drive-test`: **a check that cannot run is BLKD, which is not a pass and is not a
number.** `reach-test` now prints the car, the mode, the count-in and the clock when an arm does
not start, which is what identified this in one run rather than by guessing.

## THE PROOF THAT IT IS THIS AND NOT SOMETHING ELSE

With `API.dbgTraffic(true)` and nothing else, three runs at 2026-09-12: the body on the road read
SALOON, the mode read `endless`, the count-in read 0 and the clock read 60.0 unchanged after 150
seconds - so `step()` never ran once, which is a run that never started rather than a car that
would not move. With the real flag written into `effigyarcade.save.v1.interstate-opts` instead and
the debug switch untouched, the same arm drove 5.43 miles. One variable changed between them.
