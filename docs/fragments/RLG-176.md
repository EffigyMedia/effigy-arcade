### RLG-176 — A run often starts with an ambulance going past

TRACKED, NOT STARTED. Owner, 2026-09-08: "It's not a big deal, but pretty often a run will
start with an ambulance blowing by me."

NOT A BIG DEAL IS RECORDED BECAUSE IT SETS THE FIX'S SIZE. This is a first-impression defect:
the first thing that happens in a run is a siren going past, which spends a moment that should
belong to the road itself.

WHAT IS KNOWN WITHOUT DIAGNOSING IT. An emergency ambulance is a traffic car with the
`emergency` flag, it is exempt from the speed limit and from speed traps by design, and it is
faster than ordinary traffic by design - so it always overtakes. What is not known is why one
is so often present in the first seconds, and there are at least three candidates that lead to
different fixes:

    the spawner may simply have no start-of-run quiet period, so the first roll can put one
    on the road immediately;

    the ambulance may be spawned by an event whose timer starts at zero rather than at a
    random offset, which would make it near-certain rather than merely frequent;

    or the frequency may be correct and only feel wrong because nothing else is happening
    yet.

DO NOT GUESS BETWEEN THEM. "Pretty often" is a frequency claim, and this project has already
paid for one police defect that was diagnosed from a read and turned out to be a different
mechanism ([[RLG-173]]). Count the runs before changing a number: boot the road twenty times
and record whether an ambulance passes in the first ten seconds.
- **RULED 2026-09-08T21:59:35-04:00** — ### 2026-09-08 — counted first, and it was not "often"

**IT WAS EVERY RUN.** This record listed three candidate causes and said not to guess between
them, because "pretty often" is a frequency claim. `tools/ambulance-start-test.py` boots the road
from nothing ten times and watches the first ten seconds of each. **Ten runs out of ten opened
with an ambulance**, and the call-out clock read **0.0 seconds at the start of every one**. The
owner was being generous.

**THE SECOND CANDIDATE WAS RIGHT, AND WORSE THAN WRITTEN.** The guess was "a timer whose start is
zero rather than a random offset, which would make it near-certain rather than merely frequent".
`ambT` counts down to the next call-out and was initialised to `0` at module load, so the first
frame of the first run fired immediately.

**AND THERE WAS A SECOND HALF NOBODY GUESSED.** `reset` clears the heat, the score, the racers, the
run clock, the top speed, the wreck state and a dozen other things — and never touched `ambT`. So
it was not per-run state at all: a restarted run inherited whatever remained of the previous run's
clock. That is the more interesting defect of the two, because it is invisible on a first run and
only shows up on the second, and it is exactly the kind of thing a single measurement of one boot
would have missed.

**THE FIX IS A RANDOM OFFSET APPLIED IN BOTH PLACES**, from a named window with a committed
default. `AMB_FIRST` is 40 to 140 seconds — **deliberately shorter than the 90-to-190 gap between
later ones**, because a run is often over inside two minutes and never meeting an ambulance at all
would be a quieter road than the owner asked for. An ambulance should be a thing that happens to a
road you are already driving on; meeting one in the first seconds says the world was waiting for
you, which is the opposite of the effect.

**MEASURED AFTER: zero runs out of ten**, clock starting between 60 and 109 seconds. The check is
its own falsification — it was written and run against the unfixed engine first, where it failed
both assertions.

**A PRE-EXISTING FAILURE WAS FOUND ALONGSIDE AND IS NOT FIXED HERE.** `tools/ambulance-test.py`
asserts that the siren moves traffic out of the way, and it reports **zero cars changing lane** —
on this build and on the one before it. It is not caused by this change: the unfixed engine failed
**two** checks in that file where this one fails one, so this ruling reduced the count rather than
adding to it. The scatter belongs to the siren's own ruling and needs its own measurement, and it
is recorded in the thread rather than quietly folded in here.
- **RULED 2026-09-10T10:24:34-04:00** — **AND THE ZERO ABOVE NOW HAS A LIKELY CAUSE, 2026-09-10.** `scatter()` only asks cars between 120 and 4200 units ahead of the sounding vehicle, and measuring the player's own bar with an instrument on the loop found that **96 per cent of cars examined are rejected by that window** (EVD-623, [[RLG-205]]). An ambulance passes its own position as the origin and is subject to the same window, so a freshly spawned one may simply have nothing inside it. **This is an inference and not a measurement** - `bar-scatter-test` measures the player's bar, not the ambulance. Whoever chases the ambulance zero should point the same instrument at it before changing anything.
- **RULED 2026-09-10T14:39:16-04:00** — **AND THE ZERO IS GONE, 2026-09-10, WITHOUT THE AMBULANCE BEING TOUCHED.** [[RLG-205]] made the
scatter window two seconds of the sounding vehicle's road instead of a flat 4200 units. Running
`tools/ambulance-test.py` immediately afterwards: **"cars that moved over while it came through:
8"** - against the zero it had reported on this build and the one before it.

**SO THE INFERENCE RECORDED ABOVE WAS RIGHT, and it was still only an inference until this run.**
The ambulance passes its own position as the origin and was subject to the same window, so it was
asking a stretch of road under half a second long at the speed it travels. Nothing in the ambulance's
own path was ever broken.

**THE CHECK THAT FOUND IT WAS NOT LOOKING FOR IT.** This was a gate failing quietly in a harness
nobody had chased, and what fixed it was measuring a DIFFERENT caller of the same function with an
instrument that counted where the requests died. The lesson is the instrument rather than the fix:
`scattered` counted successes and said nothing about refusals, so a siren that asked nobody and a
siren that asked everybody and was refused looked identical from outside.
