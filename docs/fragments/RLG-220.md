### RLG-220 — A four-speed can still be dragged into fifth and sixth, and the gate clamp missed the only input that ships

**TRACKED, NOT STARTED.** Owner, 2026-09-12: *"You can still change the gear to 5 and 6 on a 4 speed,
and presumably 6 on a 5-speed. They act as neutral but the gates aren't rendered yet you can still
put the shifter there. This includes the neutral gate on the last rung too."*

---

## THIS IS THE EXACT THING [[RLG-069]] SAYS IT FIXED

That ruling's own note reads: *"AND THE KNOB CANNOT LEAVE THE RAILS THE CAR HAS. This is the half
that was missing and the half that mattered: `shiftStep` clamped to `RAIL_X.length`, which is three
whatever you are driving, so a four-speed could be dragged into slots labelled 5 and 6."*

**It fixed `shiftStep`. `shiftStep` is the KEYBOARD and the GAMEPAD.** It is what the `I`/`K`/`J`/`L`
handler calls and what the right-stick walker calls. The **drag** handler does not go through it: the
`pointermove` listener on the knob picks a rail itself, with its own loop, and that loop is

    for(let i2 = 0; i2 < RAIL_X.length; i2++)

`RAIL_X.length` is three whatever you are driving — the same constant the note names as the fault,
left in place on the path the note was not looking at.

**SO THE FIX LANDED ON THE TWO INPUTS THAT ARE OUT OF SCOPE AND MISSED THE ONE THAT SHIPS.** This
product is touch only ([[RLG-002]]); the thumb drag is the shifter. The keyboard and pad handlers are
inherited, explicitly not load-bearing, and they are the two that got the clamp.

`railCount()` already exists and already returns 2 for a four-speed and 3 above it. The drag path
simply does not ask it.

## WHAT TO DO

Have the drag path ask `railCount()` rather than `RAIL_X.length`. It is likely a one-line change, and
the reason this fragment is longer than the fix is the lesson underneath it.

**THE NEUTRAL RUNG IS THE SECOND HALF AND IT IS A DESIGN QUESTION, NOT A CLAMP.** On a five-speed the
slot below fifth is where reverse lives in a road car; this game has no reverse, so [[RLG-069]] made
it read NEUTRAL deliberately. The owner is saying the knob should not be placeable there either. That
changes what a five-speed's gate IS rather than only where the knob may go, so **ask before
building**: a five-speed with a bare third rail carrying only its top slot is one answer, and a
five-speed whose third rail is half-height is another.

**AND CHECK WHETHER THE GATE IS DRAWN CORRECTLY TOO.** The owner says *"the gates aren't rendered yet
you can still put the shifter there"* — so the picture is already right and only the hit-testing is
wrong. `gateSlots()` filters by `gearCount()`, which is why. Confirm that before changing any
drawing: this is a clamp fault, and a fix that also moves the rendering would be fixing something
that is not broken.

## THE PROOF THIS NEEDS

**It must be driven by a thumb, not by a key.** A check written against `shiftStep` passes today and
would have passed on the broken build — that is the whole shape of this defect. The proof has to
synthesise the pointer events the knob listens for, drag to the third rail in a four-speed car, and
assert the gear did not change.

`tools/shift-test.py` and `tools/shift-stop-test.py` exist and should be read first — if either
already drives the shifter, it is the place for this, and if both use the keyboard, that is worth
recording here as well.

**DO NOT START THIS WITHOUT THE OWNER'S WORD ON THE NEUTRAL RUNG.** The clamp is unambiguous; the
rung is not.
- **RULED 2026-09-12T16:10:08-04:00** — BUILT 2026-09-12, and the owner settled the rung in one line: "It's fine if it's there for 5 speed... remove it on 4 speed!" That is `railCount()` exactly as it already read - 2 for a four-speed, 3 above it - so the five-speed keeps its third rail and the NEUTRAL slot on it, and nothing about the gate's drawing changed.

THE FIX IS THE ONE LINE THIS FRAGMENT PREDICTED. The `pointermove` listener on the knob looped over `RAIL_X.length`; it loops over `railCount()` now. `shiftStep` was already right, and had been since RLG-069.

AND THE PROOF HAD TO BE BUILT TWICE, BOTH TIMES FOR THE SAME REASON: A GESTURE THAT DID NOT HAPPEN READS AS A PASS.

  (a) The first build synthesised `PointerEvent`s with an invented `pointerId`. The knob's own `setPointerCapture` throws on an id the browser has no live pointer for, so the handler died before `knobDrag` was set and the drag never armed. Every car reported the knob still on rail 0 - and "the four-speed did not reach rail 2" was satisfied by a gesture that never occurred. It printed all-green. `page.mouse` is a real input device, its pointer events carry a live id, and the capture succeeds.

  (b) Fixed, it then passed on my machine and FAILED under `step.py` on the same build, with every car back on rail 0. A fixed 1200ms wait after DRIVE was enough on an idle machine and not enough under load, so the drag landed on a plate that had no layout yet. It waits for the shifter to be visible and to have a real width now, and it refuses to drag a degenerate box.

WHAT CAUGHT BOTH WAS A SECOND CHECK ASKING THE OPPOSITE QUESTION: a car with three real rails MUST reach rail 2 on a hard drag right. Without it, "cannot reach a rail it has not got" is true of a harness that does nothing at all. That check is the reason this file is evidence rather than decoration, and it is the same shape as `badge-test`'s second question - the one that stops a check passing by deleting the thing it measures.

THE TWO OPTION STORES ARE WORTH RECORDING FOR THE NEXT HARNESS. The manual box lives in BOTH `effigyarcade.save.v1.interstate-opts` (the game's, read at start-up) and `effigyarcade.interstate.opts.v1` (the shell's pause-menu setting, applied after). Seeding only the first is silently overwritten back to AUTO, and the gate never appears.
