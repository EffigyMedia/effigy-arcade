### RLG-208 — The harness suite waits for the document, when what it needs is the engine
- **RULED 2026-09-10T18:00:34-04:00** — TRACKED, NOT STARTED. Found on 2026-09-10 while the machine could not run a harness at all.

**110 CALL SITES IN `tools/` NAVIGATE WITH `wait_until="load"`, AND THE PAGE THEY WAIT FOR IS
RUNNING.** When this machine wedged, a direct probe found `window.__road` present, `window.Arcade`
present, a canvas on the page, zero page errors - and `document.readyState` stuck at **interactive**.
The engine had booted and was answering. Every harness in the suite sat waiting for a document event
that was never going to arrive, and reported a timeout that reads exactly like a broken build.

**THE SUITE IS WAITING FOR THE WRONG THING.** No harness here cares whether the document finished
loading. Every one of them cares whether the ENGINE is up, which is `typeof window.__road ===
"object"`. A boot helper in `harness.py` - navigate on `commit`, then wait for the engine - would
make the whole suite survive a state it currently cannot run in at all.

**AND `wait_for_function` IS NOT THE HELPER TO WRITE IT WITH.** Measured on the wedged machine: the
polling form timed out after 20 seconds while a single `evaluate` after a plain wait answered
immediately. The page's own animation loop starves the poller. A fixed wait and a direct read is the
shape that worked, and `merge-mind-test.py` carries it.

**WHAT WOULD PROVE IT.** Nothing available while the machine is in this state, which is the whole
problem - the helper's value is exactly that it works when `load` does not. It can be written and
checked against a healthy machine, and the wedge reproduced by blocking the document's last pending
request.
- **RULED 2026-09-10T20:33:17-04:00** — BUILT AND NOT SIGNED OFF ([[RLG-116]]). The suite waits for the ENGINE now, and the change is
wider than the ruling described because the ruling counted only half of it.

WHAT WAS COUNTED, AND WHAT WAS ACTUALLY THERE. The ruling named 110 `goto` call sites. There were
104, and there were also 108 `wait_for_function` polls and 6 `reload(wait_until="load")` calls -
218 in all. The polls matter more than the count suggests: the ruling itself records that the
polling form timed out at 20 seconds on the wedged machine while a single `evaluate` answered at
once, so converting the `goto` alone would have moved the hang four lines down and left the suite
just as unable to run.

THREE HELPERS IN `harness.py`, AND ONE OF THEM IS THE OTHER TWO. `boot(page, url)` navigates on
`commit` and waits for the engine. `until(page, expr)` is the Python-side poll that replaces
`wait_for_function` - one round trip at a time, so the page's own animation loop cannot starve it.
`reboot(page)` is the same thing for a reload. `boot` is `goto` plus `until`.

THE URL DECIDES WHICH ENGINE, so a call site needs no second argument: a driving cabinet waits for
`window.__road`, everything else for the shell. `ready=` overrides it.

THEY RAISE BY DEFAULT, AND THAT WAS NOT THE FIRST DESIGN. `goto` and `wait_for_function` both
raised, so every call site being replaced was written expecting a loud stop; a helper that returned
False in their place would have let a whole battery run against a dead page and reported the damage
as a dozen unrelated failures. What they raise with is a READING of the page - readyState, whether
the shell attached, whether the engine is there, how many canvases - because a timeout names
nothing, and telling a broken build from a wedged machine is the whole job.

THE MEASUREMENT, TAKEN WHILE THE MACHINE WAS STILL WEDGED. Before: `load` timed out at 15s on
`interstate`, `readyState` stuck at `interactive`, `window.__road` present and answering. After:
smoke-test 6/6 where it had been 4/6, and drive-test 37/37 where neither driving cabinet could be
reached at all. The wedge cleared on its own part-way through the session, which is the third time
it has come and gone; the helper does not care either way.

THE PROOF IS `tools/boot-proof.py` AND IT MAKES THE WEDGE RATHER THAN WAITING FOR ONE. Its own
server holds one image request open forever, so `load` cannot fire while the page runs normally -
the same presentation as the real wedge. It runs its control on the LAUNCHER on purpose: the real
wedge only takes the two driving cabinets, so on a wedged machine a driving cabinet would fail
`load` with or without the fixture and the fixture would prove nothing. It asserts the negatives
too - `boot` returns False on a page with no engine, `boot(ready='road')` returns False on the
launcher, which has the shell and no driving engine, and the default raises.

THE MISTAKE WORTH KEEPING, BECAUSE IT IS THE ONE THAT ALMOST SHIPPED. Five harnesses already have a
wrapper of their own called `boot`. The mechanical conversion turned the helper's call inside those
wrappers into the wrapper calling ITSELF with the wrong arity, and drive-test went from 37 checks to
a TypeError. They import it as `engine_boot` now, and `boot-proof` asserts that NO harness shadows a
name it imports from `harness.py` - watched failing with the defect put back, then passing.

TWO THINGS IT DOES NOT COVER, STATED SO THEY ARE NOT ASSUMED. `wait_for_selector` was left alone:
Playwright polls that one in the page as well, so it is a candidate for the same treatment, but
nothing has measured it starving and this project does not fix what it has not measured.
And the proof shows the fixture and the real wedge PRESENT the same way to a harness. It does not
show they have the same cause, and nothing here explains why this machine stops firing `load`.
