### RLG-066 — A testable build is a release: push cadence for a device-tested project
- **RULED 2026-08-29T05:54:44-04:00** — **Owner, 2026-08-29, after 46 commits sat unpushed while the device tested v0.9.4:**

> "Because how this project functions, we may need to push to remote more often. But I want to avoid
> setting off GH spam triggers."

**The problem this fixes, stated plainly.** The environment rule is "do not push during work, push at
a release". That rule assumes the work can be judged where it is made. **This project's cannot.** Its
own guidance says so: rendering, audio mix, on-device layout and feel are not verified by a green
harness run, and the owner is the only instrument for them. A session of unpushed commits is a
session whose central claims are untested, and this one proved it - every device report on
2026-08-29 was made against v0.9.4 while fixes through v0.9.19 sat on a local branch.

**So the rule is not repealed, it is READ CORRECTLY for this project: a build the owner needs to test
IS a release.** Nothing about the environment rule says a release must be large. The version bump
already happens per unit, the changelog entry already happens per unit, and [[RLG-063]] now prints
the version in the arcade - so every push is a release with a number, a record and an identifier the
tester can read back.

**What actually rate-limits this, measured rather than assumed.** The repository has **no Actions
workflows** - `.github` does not exist - and the Pages deployment is `build_type: legacy`, serving
`main` at the repository root. So a push triggers one Pages build and nothing else. **GitHub
documents a soft limit of ten Pages builds per hour**, and that is the real ceiling here rather than
anything to do with spam. It should be confirmed against current documentation rather than taken
from this fragment, which is a note written from memory of it.

**Nothing about ordinary push frequency looks like abuse.** What does: force-pushing in a loop,
rewriting published history, and automation pushing continuously. None of those is this. The
practical guidance is therefore about the Pages build limit and about the tester's attention, not
about tripping a spam detector.

**The cadence:**

- **Push when there is something worth testing on the device**, not per commit and not once per
  session. Today that would have been three or four pushes instead of one, and instead of fifteen.
- **Keep it under about six pushes an hour**, comfortably inside the documented ten Pages builds.
- **Never force-push and never rewrite pushed history.** That is the behaviour that actually looks
  wrong from outside, and it is also how six shipped fixes were once silently lost in the parent
  project.
- **Tag at meaningful points, not at every push.** A tag is a record; a Pages build is a deploy.
- **Say the build number when handing something over for testing**, and expect the BUILD row in
  SETTINGS to agree with it. If it does not, FORCE UPDATE - and if it says MIXED, the service worker
  has handed the device a stale half.

**The check that would have caught this** does not exist and is worth building: nothing in the
harness suite knows the difference between what is committed and what is deployed. A session can be
entirely green and entirely invisible to the only person who can judge it.
