### RLG-229 — The non-racing class is UTILITY, and no save loses a car

**RULED 2026-09-12.** Owner, asked whether the class should be UTILITY and whether production keeps
the working wheel and knob: *"Yes, and yes."*

The question they put first is the one worth keeping: *"what I'm really trying to do is come up with
a name for a single class of non-race vehicle vehicles... The raceable vehicles are production sports
super and formula so what are the other ones?"*

---

## THE ANSWER, AND WHY THE OLD NAME WAS WRONG

The other ones are **CAB, PICKUP, VAN, SEMI and AMBULANCE**. [[RLG-213]] had already merged them
into one class on one secret unlock; only the name was left.

It was called **`traffic`**, and that name was chosen for a good reason that has nothing to do with
what the class means: it was the flag the old hundred-mile rule already wrote, so reusing it meant no
migration. **But traffic is something a vehicle DOES on the road, not a kind of vehicle.** The owner
had already said as much in a different context - *"of course those remain in traffic as well"*,
about the production cars. A class whose name is true of cars outside it is a class that will be
misread, and the four defects behind [[RLG-227]] are what misreading it costs.

**UTILITY was the owner's own word** - they had been using it since 2026-08-30 in *"production and
utility vehicles"* - and it is the only candidate that covers all five without strain. WORKING fits
the meaning better still, but the codebase already spends that word on a larger set (`WORK_BODIES`,
`isWorkCar`, `workknob`, which cover production too), and FLEET, DUTY and CIVILIAN are each taken by
the roster, the police and the driver personalities.

**THE POLICE ARE NOT IN IT.** `cruiser` and `supercruiser` are their own classes with INTERCEPT
instead of racing, and they stay that way.

## AND PRODUCTION KEEPS THE WORKING WHEEL AND KNOB

Confirmed by the owner in the same breath, and it settles something [[RLG-226]] had to leave open:
**the working wheel and the working knob are not "the utility class".** They cover production as
well, which means the treatment answers *what kind of vehicle is this* while the class answers *what
league does it enter* and *what does it cost*. Those are three different questions and [[RLG-227]] is
where they get split properly. `knob-test.py` now says so in its own words rather than leaving the
pair of class names looking like an oversight.

## THE MIGRATION, WHICH COST NOTHING

**THE CLASS HAS HAD THREE NAMES** and every one of them must still open it:

| When | Flag in the save | Paid at |
|---|---|---|
| before 2026-08-29 | `production` **and** `utility`, separately | 50 and 25 miles |
| the resort ([[RLG-213]]) | `traffic` | 100 miles |
| this ruling | `utility` | 100 miles |

`OLD_UNLOCK_NAMES` already existed for the second row, so this is one entry changed rather than a
migration written: `{ utility: ['traffic', 'production'] }`.

**THE NEW NAME IS AN OLD NAME, AND THAT COSTS NOTHING.** `utility` was one of the two pre-resort
flags, so a save from that era is answered by the first line of `unlocked` without reaching the table
at all - and it grants the whole merged class, which is exactly what the `traffic` mapping already
did for it. **[[RLG-197]] holds: a migration is never removed, and neither is its test.**

## WHAT CHANGED

`BODY_CLASS`, `RACE_BANNED`, `SECRET_UNLOCK`, `openBy`, the unlock write, `UNLOCK_HOW`'s neighbours,
and the fleet sheet's own copy of the class map. The identifiers moved with the name -
`TRAFFIC_MILES` to `UTILITY_MILES`, `wonTraffic` to `wonUtility`, `dbgTraffic` and `API.dbgTraffic`
to `dbgUtility`, and the debug button now reads UNLOCK ALL UTILITY. Leaving those spelled `traffic`
while the class was `utility` would have been the first step of exactly the drift this fixes.

The harnesses followed: `class-test`, `reach-test`, `knob-test`, `fleet-sheet` and `resort-test`.
`docs/fleet/traffic.png` is `docs/fleet/utility.png`.

**THE PLAYER-FACING LABEL NEEDED NO EDIT AND THAT IS THE POINT.** The garage note is built as
`bodyClass(optBody).toUpperCase() + ' · TEST DRIVE ONLY'`, so it read TRAFFIC before and reads
UTILITY now because the class changed underneath it. `class-test` reports the new string.

## THE PROOF

`resort-test.py` was already the migration's test and gained a row. It now boots a save holding each
of the three names in turn and asserts the whole class is offered:

    ok  the old hundred-mile flag still opens the WHOLE merged class
    ok  the utility flag opens the whole class
    ok  a save holding only 'utility' keeps every car it had won
    ok  a save holding only 'production' keeps every car it had won
    ok  the sheet agrees with the garage about the merged class

`class-test` confirms the garage note reads `UTILITY · TEST DRIVE ONLY`, `knob-test` confirms all 19
bodies still wear the finish their class demands in both games, and `smoke-test` is green.

## WHAT IS STILL OPEN

[[RLG-227]] is **not** closed by this. The name is settled and one of its four questions is answered;
the three-axis split, the two vocabularies, and the derived lists are all still proposals. And the
owner's per-game correction is unbuilt: *"the little car classes do not translate between the two
games"* - Motorsport should hold sports, super and formula only, and `garageBodies()` there still
returns COUPE, HATCH and SALOON.

**AND IT IS A RULING RATHER THAN A DEVICE REPORT.** [[RLG-231]]: the deployed build was measured at
**v0.14.1**, not the v0.13.89 three records had claimed, so [[RLG-213]] was on the phone the whole
time and no stale build ever explained the circuit garage.
